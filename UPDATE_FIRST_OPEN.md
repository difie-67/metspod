# Открытие объявления одним переходом — v4

Версия гаранта: `2026-10-04_durable-entry-v4`.

## Установка

1. Замените файлы из `metspod-v4-patch.zip` в корне проекта гаранта, сохранив пути. Архив содержит все изменения v1–v4, включая новые файлы.
2. В Railway используйте одну реплику и один polling-процесс с токеном гаранта. Остановите старые запуски, локальные копии и отдельные сервисы с тем же BOT_TOKEN. Реплики с независимыми SQLite-базами для этой архитектуры не поддерживаются.
3. Сохраните существующий постоянный том и его SQLite-базу. Для тома `/data` переменная должна быть `DB_PATH=/data/escrow.sqlite`. Если текущая база находится по другому пути на постоянном томе, сохраните именно этот путь. Не создавайте новую пустую базу вместо текущей.
4. Сначала пересоберите/перезапустите гаранта. В логе проверьте `OBRA BUILD: 2026-10-04_durable-entry-v4` и `[runtime-owner] acquired` с путём текущей базы.
5. Затем замените `escrow_bridge.py` в предложке файлом из `nft-bridge-v4-patch.zip` и перезапустите предложку. Дополнительный SQL для Supabase не требуется.

Нельзя исправить конкурирующий старый бот только загрузкой новых файлов: старый процесс с тем же токеном тоже получает Telegram-обновления. Его нужно остановить. Блокировка v4 запрещает два новых процесса на одной базе; конфликт Telegram 409 завершает процесс с понятным сообщением вместо бесконечных попыток polling.

## Новый путь открытия

Активное объявление открывается сразу. Если данные ещё отсутствуют/лот ещё подключается, вместо ошибки создаётся задание в SQLite и отправляется сообщение «Открываю объявление». Отдельный обработчик ждёт появления/активации лота и заменяет сообщение ожидания карточкой. Повторное нажатие не нужно и не создаёт второе задание. Перезапуск сохраняет задания и ID сообщения ожидания.

Та же очередь используется для кнопки покупки, если данные временно отсутствуют. Ошибки Telegram при отправке карточки/подтверждения также переводят действие в повторную обработку. Создание запроса остаётся идемпотентным, бронь возникает только после согласия продавца. Реальные статусы `inactive`, `reserved`, `sold`, `review` по-прежнему учитываются: ожидание не снимает бронь и не возвращает проданный лот в продажу.

Если за 30 минут данные так и не появились, сообщение сообщает о невозможности получить их и предлагает связаться с администратором; отсутствие строки больше не объявляется продажей, снятием лота или ссылкой чужого бота. При неисправной инфраструктуре код не может гарантировать получение данных, которых нет в используемой базе.

Успешная отправка сообщения означает подтверждение Telegram, а не прочтение пользователем. Если Telegram доставил сообщение, но ответ потерялся, или процесс остановился до записи завершения, повторная обработка может продублировать сообщение; покупка продолжит использовать ту же сделку.

## Регистрация и публикация

Гарант выдаёт постоянный `database_id` из SQLite. Предложка сохраняет его вместе с регистрацией лота в существующей таблице моста. Активация публикации и дальнейшее чтение событий предъявляют ожидаемый ID базы. Если API-запрос попал в другую базу, он получает явный отказ о несовпадении баз: предложка не должна прикреплять кнопку к неподтверждённой публикации.

Это обнаруживает разные базы API, но не объединяет их и не превращает локальную SQLite в распределённую базу. Для нескольких реплик потребовалась бы общая серверная БД для всех сделок, лотов и очередей. В текущем проекте корректная конфигурация — один сервис гаранта с одной постоянной SQLite-базой.

Старые ссылки `start=lot_...` продолжают работать. Старые записи моста без ID базы остаются совместимыми; новые регистрации используют проверку идентичности базы. При потере старой базы не восстанавливайте активные лоты вслепую: в ней могли храниться действующие брони/платежи.

## Логи

- `[runtime-owner] acquired`: `database_id`, `instance_id`, абсолютный `db_path`.
- `[deep-link] received`: тот же `database_id`/`instance_id` у обработчика Telegram.
- `[listing-entry] waiting`: сохранён переход/нажатие; `job_id` связывает дальнейшие действия.
- `[listing-entry] completed`: задание закончено, статус полученного лота.
- `[listing-entry] retrying` / `progress_retrying`: временный сбой отправки; задание сохранено.
- `[listing-entry] data_unavailable`: истекло ожидание получения данных.
- `[community-listing] database_mismatch`: активация/чтение попали в другую базу.
- `[listing-buy] availability`: фактический статус, ID брони и существующего запроса.
- `[seller-notice] delivered` / `delivery_failed`: доставка продавцу из гаранта.

Если база иногда «видит» лот, а иногда нет, сравните `database_id` и `instance_id` в соседних логах и проверьте все процессы с BOT_TOKEN. ID процесса меняется при перезапуске; ID базы должен сохраняться. Приватные ключи и полные токены лотов для диагностики не нужны.

## Проверки

Локально проверены задержка дольше прежних 8 секунд, одно задание при повторном клике, восстановление после перезапуска и после неудачной отправки сообщения ожидания, отложенная покупка, реальные недоступные статусы, таймаут без ложного «не найдено», блокировка второго процесса на одной базе и отказ API при несовпадении баз. Проверены также предыдущие сценарии комиссий, согласия продавца, уведомлений, повторной покупки и HTTP-аутентификации. Выполнена production-сборка и тесты предложки. Реальный первый переход проверяется после установки в Railway/Render.
